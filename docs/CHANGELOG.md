# Changelog

## [Unreleased]

- The Search page no longer lists stories before a search: opened fresh, it shows only the search form, and the stories and the "Stories found" count appear once words or filters are used.
- Feeds for characters and relationships: `/feed/character/…` and `/feed/relationship/…` (and `.json`), switchable under **Settings > Feeds** like the other kinds, with the link on each character and relationship page. A site that already saved its feed choices keeps them, so tick the two new kinds there.
- **Back up now** on the Backups screen now returns to the Backups screen when the backup is finished (a backup started from the Updates screen still returns to Updates).
- **Maintenance > Security events** is now called **Logs** (the address is unchanged), and the matching setting heading on the Spam protection screen follows.
- A rating is now mandatory. Every story needs exactly one rating before it is published or sent for approval; a draft still saves without one. The rating cannot be switched off any more: under **Classification** it is shown ticked and locked in the required kinds, and a hand-made request that leaves it out changes nothing. A new site starts with four ratings (General Audiences, Teen And Up Audiences, Mature, Explicit and Not Rated, so an author can say a story is not rated and every story still has the information defined), and a site updated to this version that has no ratings is given the same four (migration 0036; a list that already exists is never touched, and choosing a rating starter list at install replaces them). The last rating writers can choose cannot be hidden or deleted. Stories published before this keep showing, with "Not rated" on the card and the story page, are marked "No rating" in the story list (with a **Rating** filter), and their story form asks for one; the next save needs it.
- Feed links on the pages they belong to. An author's page, a fandom, character, relationship, genre or tag page, a story and each of its chapters, and the news page and posts now point to their own feed: in the head of the page (RSS and, while it is on, JSON Feed, plus the story's comment feed while it is offered), and in a visible "Feed for …" link just below the page's title in Storybook, Rosewine, Lavender Mist and the built-in theme (a new template tag, `lf_feed_link()`). A **Feed** link (and a **News feed** link while news is on) now also sits in the footer of every public page, through the existing footer link list so any theme shows it. Nothing is advertised for a missing page, a switched-off kind or an archive that requires sign-in.
- Search engines. **Settings > Search engines** adds **Ask search engines not to index this site**, which puts a noindex tag on every public page, makes `robots.txt` disallow everything and stops publishing the sitemap. Otherwise the site publishes `/sitemap.xml` (an index of parts, each at most 10,000 addresses, listing public stories, the authors who have one, the classification pages people can browse, the news page, published news posts and published pages not marked noindex; never a draft, an unpublished story or one waiting for approval) and a virtual `/robots.txt` that keeps crawlers out of the admin, account, search and download addresses and names the sitemap. Both answer a matching `ETag` with a `304`. Story and chapter pages now name their own address as the canonical one.
- Redirects. **Settings > Redirects** sends visitors from an old address to a new one (permanent 301 or temporary 302, to a path on this site or a full https address). A redirect is used only where the site has nothing to show, so it never hides a page that is there, and one that would loop is refused. Changing a static page's address, or merging a classification term into another, adds a permanent redirect from the old address automatically (story addresses never change). New migration 0037.
- Settings export and import. **Settings > Export and import** downloads the portable settings (Archive, Security, Privacy, Comments, Downloads, Feeds, News, Front page, Editor, Retention, Search engines and the theme choice) as a versioned JSON file, and reads one back with a before-and-after list shown before anything is applied. The site address, the administrator's email, the secret key, the table prefix, the database details, the trusted proxy list, the privacy-policy page number and spam keys have no place in the file. A file in an unknown format version, with an unknown group or setting, or with a value its own settings screen would refuse or quietly change is refused as a whole. The format is described in `docs/SETTINGS-FILE.md`.
- Feeds. Readers can follow the archive in a feed reader. Each feed is RSS and, unless switched off, also a JSON Feed at the same address with `.json` added: `/feed` (recently published and updated stories, a story that is updated comes round again), `/feed/author/{author}`, `/feed/fandom/{fandom}`, `/feed/genre/{genre}`, `/feed/tag/{tag}`, `/feed/story/{story}` (that story's new chapters, newest first, each with its end note after the text and the story's cover as the picture), `/feed/story/{story}/comments` and `/feed/news`. A feed lists only what a visitor can read: a draft, an unpublished story, a story waiting for approval, a story with no published chapter and a comment waiting for approval never appear, an author is named by display name only, and an author, fandom, genre or tag with nothing public answers not found like its page. An archive set to **Require sign-in to read** offers no story feed at all (the news feed stays open, as the news page does). Feeds answer a matching `If-None-Match` with `304 Not Modified` and carry an `ETag` made from the content, so a removed or unpublished story always changes it. Every public page now advertises the site feed and the news feed in its head for feed readers. **Settings > Feeds** chooses which kinds of feed exist (the per-story comment feed is off by default and also needs comments to be on), whether JSON Feed is offered, how many entries each feed holds (5 to 50, default 20) and whether an entry carries the whole text of a chapter or news post or only its opening.

## [1.3.0] — 2026-11-08

- Story cards on the indexes (home, Browse, search, an author's page, bookmarks, Continue reading, Updated stories) now show how many chapters a story has, such as "Ongoing · 12,345 words · 12 chapters · Updated 21 October 2026", counting published chapters only. Themes get the new `chapters` entry on each card (`story-card` in the bundled themes); a theme that does not print it simply leaves it out. Each card also lists the story's rating, archive warnings, fandoms, characters, relationships and tags as links to their pages (a long list is cut short with "and N more"; genres and categories stay on the story page), read for the whole page at once.
- Admin dashboard: the **Quick links** card is gone (Archive settings and System information are in the menu).
- Updates screen: release notes now read as formatted text (headings, lists, bold, code and links) in a box that scrolls once it is long, instead of the raw Markdown. They pass through the same text cleaner as chapters, so a release body can never put a script, an outside image or a clickable `javascript:` address on the screen, and every link opens in a new tab without passing on where it came from. The screen also shows, at a glance, the installed version with the database schema and the install folder, the update status as a badge (up to date, update available, not checked yet, check failed) with the channel and when the last check ran, and the update source with a link to all releases. **Latest release** shows the release name, a Stable or Pre-release badge, the published date, **View release notes on GitHub** and **Download release ZIP**; a release that is not newer than the one running has no download button and the screen says why. New panels: **Database updates**, **Full backups** (the three newest, with Download, Restore, Delete and **Back up now**, from the same code as the Backups screen), **System status** (a Pass or Fail table for PHP, extensions, downloads from GitHub, file permissions, disk space and the update storage folder, run by the same checks the review screen uses) and **About updates**. Update settings gain an **automatic check** (off by default, daily or weekly, made the next time an Administrator opens an admin page once one is due, never by a background job, and it only looks: nothing is downloaded or installed) and an optional **GitHub token** that lifts GitHub's limit on anonymous requests (kept in the settings, shown only as Set or Not set, never logged, sent only to GitHub's API). When an update is available the Updates entry in the admin menu shows a mark. The history gained a Version column and a plain sentence for each result.
- After new files are uploaded over an existing site, the Administrator whose visit applies the waiting database changes now sees one note, once, saying how many were applied ("Applied 3 database changes after the new files were uploaded."), and the activity list says the same. Nothing is shown when nothing was waiting or when a change failed (the critical alert stays the only signal then), and nobody else sees it.
- Replies to chapter comments, one level deep. A signed-in person can reply to a published comment with a **Reply** link; a reply to a reply is not possible, which keeps the list readable on a phone. Replies sit under the comment they answer, oldest first, marked "Reply to {name}" for screen readers, and a page of comments is counted in conversations so a thread is never split across pages. Hiding or marking a comment as spam hides its replies and restoring it brings them back; deleting a comment deletes its replies and asks first, saying how many go with it. A reply is held, throttled, spam-checked, reported and moderated by the same rules as a comment. The writer is told of a new reply as of a comment, and the person replied to is told once (the profile choice now reads "Email me when someone replies to my comment, or the writer answers a chapter I commented on"). **Settings > Comments** has **Allow replies** (on by default); switched off, the reply links go and existing replies show in the ordinary list. The Comments screen marks replies, links to the comment each answers and can show replies only. Needs a database change (a `parent_id` column on comments, applied the first time an Administrator opens the admin). Themes: `parts/comments.php` now draws each comment through a new `parts/comment.php`, with the classes `lf-comment__replies`, `lf-comment__reply` and `lf-comment__action--reply`.
- The colour choice in the header of Storybook, Rosewine and Lavender Mist is now one button instead of a dropdown. Each press steps through Auto (match the device), Dark and Light and shows the mode with an icon and a short label; its accessible name says what it does and what the next press will do ("Colours: matching your device. Press for dark"). The saved choice and the account setting are unchanged. Quick presses are now saved to the account once, after a short pause, so a reader who presses several times no longer ends up with an in-between value on their account.
- Visitors can choose their own theme (off by default). **Appearance > Themes** has **Let visitors choose their own theme** and a list of the installed themes to offer; the site's active theme is always offered. When two or more themes are offered, themes print a small form (a list and a button, working without a script) through the new `lf_theme_switch()` tag. A signed-in reader's choice is saved on their account and follows them to any device; anyone else gets a cookie that holds only the theme's folder name (`SameSite=Lax`, `Secure` on HTTPS). A name that is missing, not offered, switched off or no longer compatible falls back to the site's theme. The admin, downloads, feeds and the installer always use the site's theme. Pages vary by cookie when the feature is on. A theme's options stylesheet is now requested by theme name (`/theme-options.css?theme=…`), so one theme's options are never served under another.
- Administrators can preview any installed theme on the whole site. **Appearance > Themes** has a **Preview** button on every theme but the active one (and `?theme=folder-name` on any public address does the same for a signed-in Administrator). The theme shows on every public page, to that Administrator only, with a banner (new tag `lf_theme_preview_banner()`) that offers **Make this the active theme** and **Exit preview**. The preview lives in the Administrator's session, is checked against the installed and compatible themes on every request, is never served from a shared cache, ends on sign-out, and ends by itself if the theme is deleted or no longer fits.

- Rosewine and Lavender Mist: a story that is read on its own page (one chapter, marked Completed) now shows its text in the same card a chapter page uses, with a gradient heading ("The story" and the word count) above the reader controls, instead of loose text on the page. The details above it (status, length and dates, fandoms, characters and tags, summary, notes and disclaimer) now sit together in a quieter panel with an accent bar, so the details and the text read as two different things. The panel appears on every story page in both themes, with light and dark colours.

- Updater: the first update on a site that has never used the updater before (every site installed before 1.2.0) now adds the plugins and themes the new release introduces. Until now it had no record of what the earlier release shipped, assumed every missing bundled plugin or theme had been removed on purpose, and left it out, so the new Rosewine and Lavender Mist themes were not installed by the update to 1.2.0. Only Visitor Stats and Dummy Content, the two bundled plugins that earlier releases shipped, are still treated as removed when missing. A site that was already updated to 1.2.0 this way can add the two themes from **Appearance > Themes > Add a theme**, or by uploading their folders from the release ZIP.

## [1.2.0] — 2026-11-08

- Two new bundled themes, **Rosewine** (deep wine, dusty rose and blush on warm cream) and **Lavender Mist** (soft teal, lilac and iris on cream), both with light and dark colours and the same reader controls as Storybook. Gradients sit on the header and footer, buttons, section headings, story and news cards, tags, and the heading of a chapter, page or news post, which are drawn as one rounded card; the text itself stays on a near-flat surface. Dropdowns (the reader's text size and reading width, the colour choice, and the select boxes on the search and account forms) are restyled, and in browsers that cannot style the browser's own list, a small script in the theme draws a matching list that works with the keyboard and screen readers and falls back to the ordinary select without scripts. Switch themes under **Appearance > Themes**; Storybook stays the default.
- Appearance: the Add a theme notice now reads "Upload a .zip archive containing a theme folder. The destination folder name is derived from the theme's declared name.", and a theme's Details list Author, Design URI, Version and Folder (a theme can declare a `Design URI:` line in its stylesheet header, shown as a link). The Needs, Source and In use lines are gone; a theme the site cannot use still shows the reason.
- Chapter comments. Signed-in readers can leave a plain-text comment under a chapter (links are shown as text, never clickable); a story's own writer's comments carry an **Author** badge. A person's first comment is held for approval by default, a comment the spam checks suspect is kept as spam rather than dropped, readers can report a comment (several reports hide it until a moderator looks), and a commenter can edit their own words for a short time and delete them at any time. Writers can turn comments off for a story or a chapter. **Settings > Comments** sets the site switch, the approval rule, the edit window and the report limit. A new **Comments** screen lists every comment by state with counts, filters and bulk actions, and shows a count beside the menu entry and on the dashboard; writers see only the comments under their own stories. Writers are notified of new published comments (and by email if they choose), readers can ask to be emailed when the writer answers, and a reader's data export includes their comments. Themes print the section with a new `lf_comments()` tag.
- Classification lists: every term has a tick box, with a select-all box in the header, and **Approve**, **Mark as unapproved** and **Delete** act on the ticked terms in one step (or on every match, up to 500, after confirming the exact count). The old "only those not yet reviewed" box is now an **All / Approved / Unapproved** filter with counts, and the screens say Approved and Unapproved instead of Reviewed. The old `?unreviewed=1` address still works.
- Moved sites are noticed. If the address or the folder the site runs from no longer matches what was saved, the admin shows an alert that leads to a screen suggesting the new address; you confirm or correct it, or keep the old one for a site meant to answer under two names. The address is never changed without that confirmation, and `config.php` is rewritten only for the `site_url` line (or you are shown the line to change by hand).
- Visitor Stats now counts signed-in readers too. A signed-in person opening a story or chapter adds one view exactly like anyone else, anonymously: nothing about the account is read or stored, and the story's own author is counted like any other reader. Previews, drafts, pending and unpublished stories, robots and background prefetches still never count. Earlier totals only held readers who were not signed in and are not recalculated, because those past views were never recorded.
- Backup files now start with the script name: a new backup is stored and downloaded as `LumoraFiction_20261105-123456-a1b2c3d4e5f6-files.zip`, `…-database.sql.gz` and `….json`, so an archive in a downloads folder says what it belongs to. The backup's own code (its id) is unchanged. Backups made earlier keep their file names on the server and still work in every way (listed, checked, restored, deleted), and are downloaded under the new name too; nothing is renamed. The safety backups made before an update or a restore use the new names as well.
- Updates screen: the check for a release on GitHub and the upload of a release ZIP are now two tabs, **GitHub** and **Manual Update**, with one panel showing at a time; the settings and the history stay below and apply to both. The tabs work with the keyboard (Left and Right arrows, Home and End) and without JavaScript (each is a link to `?tab=github` or `?tab=manual`). The screen opens on GitHub, on Manual Update after a refused upload, and on Manual Update when the last check could not reach GitHub, with the reason shown. The tab bar is a reusable admin component, `Tabs`, that plugin screens can use too.
- Admin banner while the site is offline: when maintenance mode is on, by hand or inside a scheduled window, every admin screen shows a banner (for people who can manage the site) saying that the public site is offline for visitors, that administrators still see it normally, whether it was switched on by hand or by a schedule and when it ends (in the site's time zone), with a link to **Maintenance mode**. While an update or restore is running, the banner says so instead and links to the progress screen, never to a switch. The dashboard has a new **Site status** card showing the same. The state is not a site alert, so the alert count and the alert email are unchanged.
- The admin sidebar is rearranged. **Alerts** is now its own item directly under Dashboard and shows the number of open alerts beside it (the same number as the header link). **Plugins** is its own item directly after Appearance. **Users** is now a group with **All users** and **Privacy requests**. **Maintenance** lists Updates, Backups, Maintenance mode, Security events and System Information, in that order. No address changed, so bookmarks and links keep working. Plugins that add a child to the Maintenance group still land there; the menu slugs that moved are listed in the developer guide.

- **PHP 8.2 is no longer supported; the minimum is now PHP 8.3.** PHP 8.2 stops receiving security fixes on 2026-12-31. PHP 8.3, 8.4, 8.5 and 8.6 are supported. A site still running PHP 8.2 cannot be updated to this release: the updater's compatibility check refuses it before anything is replaced, and a new install on 8.2 is stopped at the requirements check. Ask your host to switch the site to PHP 8.3 or newer before updating. Visitor Stats and Dummy Content now declare PHP 8.3 as well.

- Privacy: **Settings > Privacy** names a published page as the privacy policy, which the registration form now links to (a new template tag, `lf_privacy_link()`, lets any theme link to it), and chooses what happens to the stories of a deleted account: keep them under a neutral author name (the default, "Anonymous author") or delete them. **Maintenance > Privacy requests** lets an Administrator who manages users find an account by email address, **export its data as JSON** (account details, stories and chapters, bookmarks, reading places, follows, notifications and the activity log; never the password hash, a token or anyone else's details) and **delete the account**, after typing the person's display name. A member can do the same for their own account from **Your data and privacy** on their account page (deleting asks for the password, and an author chooses there whether their stories are kept under the neutral name or deleted; an Administrator deleting from Privacy requests makes the same choice for that request, with the site setting preselected). Deleting removes the email address, login name, display name, password, author text and picture, bookmarks, reading history, follows and notifications, and the network addresses in the activity log; the account row stays, anonymised, so kept stories still have an owner, and it can never sign in again. The last active Administrator cannot be deleted. Exports and deletions are written to the activity log by account number. New `account_deleted` action and `lf_privacy_policy` filter. The Users screen shows a deleted account and refuses to change it.

- Static pages: **Pages** in the admin menu (Administrators) creates About, FAQ, Terms of Service, Privacy Policy and any other page, each at its own address directly under the site address (`/about`). A page has a title, an editable address (lowercase letters, digits and hyphens; refused when the site already uses it, for example `search`, `news` or a plugin's address, or when another page has it), text in the same four editors and the same sanitiser as a chapter, a draft or published state with a preview that only the Administrator can see, a menu and footer placement with an order, a description and canonical address for search engines, and a switch asking them not to list it. Published pages in the menu join the main menu, and those in the footer are drawn by a new `lf_footer_links()` template tag, added to both bundled themes with dark-mode styles. An empty list offers one-click placeholder drafts. A draft, or a deleted page, is never linked and answers the not-found page; pages stay readable when the archive asks visitors to sign in. A new database table holds the pages, and the public site keeps working if files are uploaded before it exists. New `page_deleted` action and `lf_footer_items` filter.

- Chapter end notes and story end notes: besides the notes above a chapter, a chapter has **End notes** shown below its text and above the chapter links, and a story has **End notes** shown on the story page after the chapter list and, once the story is marked Completed, after its last chapter. Both are plain text up to 4,000 characters, optional, escaped like the existing notes, kept in a chapter's earlier versions (and restored with them), copied when a story is copied, and included in EPUB, PDF and HTML downloads. Drafts never show them. Existing stories are untouched. The template fields are `chapter.end_notes` and `story.end_notes`, with the classes `lf-chapter__end-notes` and `lf-story__end-notes`, styled in both bundled themes. A new database change adds the columns.

- Staff-created terms are approved at once: a fandom, character, relationship or tag that an Administrator adds while editing a story is stored as reviewed, and renaming an unreviewed term, adding or removing an alias, or describing it marks it reviewed in the same step, so the **not yet reviewed** list holds only writers' proposals. A writer's proposal stays unreviewed, editing a reviewed term changes nothing, an edit that fails approves nothing, and merging does not approve the target. The activity log shows when an edit approved a term.

- **Settings > Archive > Writers may propose new tags** (on by default, so nothing changes until it is switched off). When it is off, a writer picks tags from the list the Administrator keeps instead of typing new ones, a new tag typed into a hand-made request is refused, and tags writers already proposed stay on their stories and in the list, where they can still be reviewed, merged or given aliases. The tag list under Classification can then be put in order by hand, like the other curated lists. Fandoms, characters and relationships are not affected.

- PHP 8.6 compatibility: sessions kept in the database now work on PHP 8.6. The session storage did not supply its own session identifiers, which PHP 8.6 reports as deprecated, and the site turns every such notice into an error page, so on 8.6 any page that started a session showed "Something went wrong". Nothing changes on PHP 8.2 to 8.5.

## [1.1.0] — 2026-10-27

- The database part of a backup (made before every update and on demand) is now written in one linear pass instead of rescanning the table for every page of rows. A table with hundreds of thousands of rows used to take minutes and could run into the web server's time limit, which stopped the update at "Create update backup"; it now takes seconds, and the backup file is exactly the same. A backup that was started before the change still carries on.

- Updates, backups and restores now show their progress without reloading the page. Each step is still a request of its own, as before, but the steps and the list of what has happened are redrawn in place, with a "still working" line while one runs, and the page stops on the usual **Resume** and **Cancel** buttons if a step does not finish. If anything unexpected happens (the connection drops, a step takes more than two minutes, the answer is not understood) the page falls back to the ordinary form, which shows what happened, so no run is ever lost; with JavaScript turned off, **Continue** works as before.

- Visitor Stats can import the country data from a file already on the server, which is the reliable way for a file too big for a browser upload: put the GeoLite2 ZIP (or the two CSV files) in `storage/visitor-stats/incoming/` and press **Import**, or type the full path of a ZIP or folder. The import then carries on by itself and shows how far it has got, the old data stays in use until the new data is finished, and an alert appears when the data is more than six months old.

- **Maintenance > System Information** now shows the **Install folder** of the site, the absolute path on the server, so an Administrator knows where to place a file. It appears on the screen only and is left out of the downloadable snapshot, like the table prefix.

- Upgrading by uploading files: version 1.0.0 has no Updates screen, and database changes were applied only by the installer and the updater, so new files uploaded over a 1.0.0 site met an old database. Now, when an Administrator opens the admin and database changes are waiting, they are applied once, under the existing lock, and written to the activity log (as "applied pending database changes after new files were uploaded"). Nobody else triggers it, public pages never do, and it is skipped while an update runs, because the updater applies its own changes in a fixed order. If a change fails, the admin still opens and a critical alert, with the details in the error log, says so.

- System Information no longer shows a second, misleading "Installed version" row. The version of the application is now read from one place only, the version file shipped with the code, so it can never disagree with itself. The installer used to store a copy in the settings that nothing updated, so an updated site kept showing the version it began with; the copy is no longer written, and a new database change removes the one existing sites hold.

- The dashboard's **Recent activity** now reads as plain sentences, such as "Dev Admin turned on the Visitor Stats plugin" or "Ann published a story “Winter”", with dates like "27 Oct 2026, 20:13", instead of showing the log's internal names. An action without a written sentence still reads as words and never as a raw code.

- Story downloads: readers can take a published story away as an **EPUB** (EPUB 3, with a cover when the story has one), a **PDF** or a single self-contained **HTML** page, from a **Download** button on the story page. Each file has a title page (title, the author's display name, summary, rating, warnings, fandoms, characters, relationships and tags), the chapters in order and chapter notes; the Author's sign-in name never appears in a file or its name. **Settings > Downloads** switches downloads on or off for the whole site, chooses the formats, and decides whether download totals are kept and shown beside each format (plain totals for each story and format, nothing about who downloaded). Each Author can refuse downloads for all their stories (a **Downloads** box on their Author profile, allowed by default) and each story has its own choice (use my default, allow, or refuse), which wins over the default in both directions; nothing an Author chooses has any effect while the site switch is off. Only a published story with a published chapter can be downloaded: a draft, a story waiting for approval, an unpublished or trashed story, a refused story, an unknown format and a switched-off feature all answer the ordinary not-found page, and an archive that requires sign-in to read also requires it for downloads. Files are made on first request and kept under `storage/cache/downloads/`, named by what they show, so a changed chapter, chapter order, publication or detail gives a new file and removes the old one; one build runs at a time for a story. PDFs are made by the bundled Dompdf library (see `docs/THIRD_PARTY.md`) and only for stories of up to 100,000 words and within the host's memory limit; a longer story gets a plain message pointing to EPUB or HTML. A file sent to a signed-in reader is never kept by a shared cache. A new template tag, `lf_downloads()`, and a `parts/downloads.php` part draw the menu in both bundled themes, with dark-mode styles. New database changes add the per-story choice, the Author's default and the totals table.

- Visitor Stats, a new bundled plugin (off until switched on under **Maintenance > Plugins**, and counting off until **Count views** is ticked on its screen). It counts one view each time a reader who is not signed in opens a story or chapter page; signed-in people, previews, drafts, pending and unpublished stories, search robots and background prefetches never count. Only day-level totals are kept, so no row belongs to one reader: no cookies, no IP address, no browser text, and only the domain of another site as a referrer. The dashboard gets a card (today, 7 days, 30 days, all time, and the most read stories of the week), a **Visitor stats** screen shows views over time (7, 30 and 90 days), the most read stories, referrers, browsers, devices and countries, and an Author sees the views of their own stories on each story's screen (Editors and Administrators see every story's). Countries come from a GeoLite2 CSV the administrator imports in steps, kept as a file under `storage/`; nothing is bundled or downloaded, and the screen reminds when the data is over six months old. Three additions for plugins: a `story_viewed` action, `admin_dashboard_cards` and `admin_story_panels` filters, and `$kernel->root`.

- Updater, backups and rollback: **Maintenance > Updates** checks GitHub for a newer release when an Administrator asks, or takes an uploaded release ZIP, and shows a review screen before anything changes. The package is verified against the SHA-256 checksum published with the release (a download without one is refused; an upload can be checked against a pasted checksum), every PHP file in it is parsed, and no entry can write outside the site. Checks cover the version (updates only go forward), the PHP version and extensions and the database server the release needs, a database from a newer release, folders the web server cannot write to, and free disk space. Confirming runs the update one step at a time on a progress page (so a host's time limit is never hit, and a large database is backed up in pieces): close the site to visitors, back up the files, back up the database, install the files and apply the new database changes, check the new version. Nothing is replaced until a verified backup exists, and after that any failure restores the files and the database by itself. An interrupted update can be resumed or cancelled, and cancelling after files were replaced puts the earlier version back. Configuration, uploads, logs and any plugin or theme the release does not ship are never touched; a bundled plugin or theme you removed stays removed. Every update, restore and backup is kept in a history and an update log.

- Backups: **Maintenance > Backups** lists the backups in `storage/backups/` (a ZIP of the application files and a copy of the database), makes one on demand, downloads either part (Administrators only, streamed through the application and recorded in the activity log), restores one after a confirmation page (with a safety backup of the present state made first) and deletes one.
